# 长期核心需求与开发约束

记录日期：2026-10-01。来自仓库拥有者的持续需求；用于后续设计、PR 与验收，不是已实现功能清单。具体阶段见 [开发计划](DEVELOPMENT_PLAN.md)。

## 不可偏离的产品方向

1. **易使用**：房主 Windows EXE 安装和管理；朋友只用可信 LAN 浏览器，输入身份与验证密钥。普通玩家不需要学 Git / Python / Node / 提示词工程。默认流程从选择玩法到入座尽可能短；高级选项逐步展开。
2. **模块化**：账号、权限、房间、权威事件与提交机制构成小内核；规则、AI 主持、地图、骰子表现、主题 / 美术、TTS / 台本、成长 / 经济等可独立扩展。添加普通模块不应改宿主 UI 大文件或重新构建核心。
3. **文档周全**：用户指南、世界书 / 角色 / 剧本 / 预设教程、插件 SDK、规则适配器开发、字段参考、可运行例子、测试与发布 / 升级 / 回档 / 排错，随代码版本维护。
4. **生态健全、易拓展**：标准创作格式、可视化编辑与 CLI 脚手架、版本 / 依赖 / 许可 / 来源、测试和审核、社区提交、作品发现、更新与迁移，构成完整闭环。不能只堆一个下载列表。
5. **多种玩法**：AI 跑团、世界书 / 规则导入、角色信息、房主开房与多人协作是基础；支持拓展到自由叙事、调查冒险、D&D 类规则、类 SLG / 模拟经营等。
6. **预设库与社区创作**：玩法预设可组合世界、剧本、角色模板、规则与插件；官方提供可实际试玩的样板，第三方可以开发、发布、派生和更新自己的预设。
7. **以真实需求决定优先级**：研究酒馆 / AI RP / TRPG 玩家与作者，区分公开需求信号、假设和真实用户反馈，不制造“全社区最热门”排行榜。

## 保留的基础需求

- 主要是用户与几位朋友的小团体游戏，不以商业多租户 / 集群平台为第一目标。
- 保留演示、AI 主持、人类主持 / AI 辅助、可配置模型服务；不强制绑定某个付费供应商。
- 世界书、角色、玩法与插件有标准模板，便于别人创作。
- 主题 / 美术、地图、TTS / 台本、骰子和后续系统都有扩展空间。
- ComfyUI Desktop 是桌面技术栈 / 实例管理布局参考，保留余烬自己的品牌，不复制不兼容许可的实现。

## 工程底线

- AI 提议，服务器验证并结算；不能让模型虚构权威骰子、直接改权限或任意改核心数值。
- 文字世界书不等于可执行规则；D&D / SLG 不应伪装成一段“严格遵守规则”的提示词。
- 内容包、提示词配置、模型连接、UI 表现、可执行插件分别管理；预设不携带 API key、账户、会话、私有备份，也不自动获得代码执行授权。
- 隐私在服务端投影；权限 / 密钥撤销不随剧情回档复活。受信任 Python 不是沙箱。
- 持久状态、存档 / 回档、幂等、冲突、迁移、依赖和版本可追溯；崩溃 / 断线不靠“重开一个房间”解决。
- 当前单 worker、SQLite、小房间边界保留，除非新的需求和验收证明必须改变。
- 任何对外“可用”声明都有实际构建 / 测试 / 下载证据；beta、网络、费用、签名与实机限制如实说明。

## 每个 PR 的检查问题

- 新手是否少了一步，还是新增了一堆必须填写的设置？
- 它属于宿主、规则、模块、世界 / 剧本内容还是表现层？边界是否说清？
- 作者能否只用公开契约完成同样的作品，不依赖内部变量 / DOM？
- 文档、示例、schema、兼容性、迁移、权限 / 回档测试是否一起更新？
- 老房间 / 老作品如何继续使用？能否检查失败原因与恢复？
- 所需许可、代码信任、外部网络和可能费用是否明示？
- 是否真正支持多人和玩家自主选择，还是只有演示对话看起来成功？
