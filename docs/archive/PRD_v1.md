# 余烬酒馆 · 轻量多人 AI 跑团工作台

**产品需求文档 PRD v1.0**  
日期：2026-09-30  
交付状态：可运行 MVP；真实模型接口已实现并完成模拟服务契约测试，尚未使用真实密钥联网验收。

> **一句话定义：** 让一位房主和一桌玩家，使用统一世界设定、受控的 AI 主持与可恢复的游戏状态，在线完成一场轻规则叙事冒险。
>
> 本项目不是 SillyTavern 的全功能复制，而是围绕“多人同桌跑团”重新设计的原创、轻量 Web 应用。第一版先验证完整游玩流程，不承诺实现所有线下规则与工具。

## 1. 已确认的产品决策

| 项目 | 本次确认 | 对首版的影响 |
|---|---|---|
| 玩法 | 通用轻规则 | 不绑定 D&D 5e 或 CoC 规则书；有属性、骰子与明确失败代价 |
| 主持 | AI 主持，房主可干预 | AI 叙事与提出检定；房主可补述、取消检定、改设定、维护角色和回档 |

| 首次体验 | 无密钥演示 | 明确标注本地规则脚本，不伪装为外部 AI；用于验收产品流程 |
| 交付 | 全栈源码、预构建前端、PRD、部署与测试说明 | 可在自己的机器或单台服务器运行；当前提供临时在线预览 |

## 2. 用户问题与产品价值

### 2.1 需要解决的真实问题

1. 同伴分散在不同地方，聊天、角色卡、骰子和主持资料散落在多个工具中。
2. 通用 AI 聊天容易忘记角色生命、道具、已确认事实，或把被否决的情节继续当成现实。
3. 多人共享同一段剧情时，谁能操作哪个角色、谁能改设定、谁能回档不清晰。
4. 玩家希望重新尝试分支，但“删除后面几条聊天”不能正确恢复属性和物品。
5. 工具配置复杂，第一次游戏还没开始就被模型、插件和上下文设置消耗耐心。

### 2.2 首版的价值主张

- 一个房间内共享设定、角色、行动、检定和历史。
- 初次试玩不需要 API 密钥；正式模型配置只在服务端完成。
- 用服务器维护权威状态，不依赖模型记住所有数字。
- 每个事件都有快照；回档后将旧未来封存，并从当前上下文排除。
- 人类房主始终拥有最终干预权。

### 2.3 第一轮验证目标

邀请 1 位房主、2–4 位玩家，完成一次 30–60 分钟的试玩。重点不是统计生成文字的数量，而是观察：

- 玩家能否在没有开发者陪同的情况下入房、获得角色并提交行动？
- 大家是否相信、看得懂检定结果与状态变化？
- 回档是否真正恢复了他们预期的游戏状态？
- AI 是否尊重世界设定和玩家选择，而不是自说自话？
- 哪些功能不做会让游戏中断，哪些只是“看起来很酷”？

## 3. 产品范围与优先级

### 3.1 P0：本次已实现

| 模块 | 首版功能 | 明确边界 |
|---|---|---|
| 账号 | 用户名注册、密码登录、退出、登录有效期、游客试玩 | 无邮箱验证、密码找回、第三方登录 |
| 房间 | 创建、世界预设、自定义前提、6 位邀请码加入、我的房间列表 | 每房最多 12 位成员；无公开房间广场、踢人、邀请码轮换 |
| 实时同步 | WebSocket 状态广播、在线成员、自动重连；掉线时定时刷新兜底 | 单进程部署；不声称支持多节点协同 |
| 世界书 | 世界名称、前提、基调；地点/NPC/道具/传闻条目与关键词 | 首版全部公共可见，没有主持秘密区 |
| 角色 | 新建、编辑、移除；属性、生命、压力、简介、物品；房主分配操控者 | 最多 12 个角色；一位成员最多绑定一个角色；房主可代操控 |
| 行动 | 角色行动、AI 主持回复、主持链路标签、人工补述 | 没有强制轮流或战斗先攻顺序，按到达与版本校验串行提交 |
| 骰子 | 服务端自由掷骰、d20 属性检定、结果与失败代价记录 | 非完整战斗系统；自由掷骰不自动改变属性 |
| 双模型 | Gemini 知识顾问；OpenAI 兼容决策模型；结构化输出验证 | 真实联网效果和具体模型兼容性需密钥验收 |
| 历史与记忆 | 持久事件、每事件快照、有效时间线关键词检索、最近事件上下文 | 非向量检索；没有跨房间长期记忆与自动长篇摘要 |
| 回档 | 房主选择有效节点、完整叙事状态恢复、后续事件封存、新分支广播 | 是线性新分支，不是可自由切换的多分支树；暂无重做/恢复封存分支 |
| 导出 | 房主导出 JSON，含当前状态、完整有效/封存事件与快照 | 暂无导入按钮；完整数据库备份另有脚本 |
| 界面 | 冒险大厅、冒险现场、世界书、角色档案、事件档案、主持设置 | 桌面与手机布局、明暗主题；无语音或视频 |

## 4. 用户与权限

### 4.1 角色定义

- **房主**：创建房间的人，也是本房的人工裁定者。
- **玩家**：持邀请码加入的登录用户，操控分配给自己的角色。
- **游客体验账号**：具备房内基本操作能力，但不能开启真实付费模型；退出后没有密码找回路径。
- **AI 主持**：只返回受约束的建议与叙事，不是具有账号权限的成员。
- **部署维护者**：管理服务器、模型密钥、数据库与备份；不是普通房间玩家。

### 4.2 权限矩阵

| 操作 | 房主 | 玩家 | 模型 |
|---|---|---|---|
| 查看房内公共资料、有效历史 | ✓ | ✓ | 经服务端按需提供 |
| 角色行动/角色检定 | 任意当前角色 | 仅被分配角色 | 只能提出检定建议 |
| 自由掷骰、场外聊天 | ✓ | ✓ | 不执行 |
| 新建/编辑/移除角色 | ✓ | ✗ | ✗ |
| 分配操控者、修改世界书 | ✓ | ✗ | ✗ |
| 补述、重试主持、取消检定 | ✓ | ✗ | ✗ |
| 开启真实双模型 | 正式账号且服务端已配置 | ✗ | ✗ |
| 回档、看封存记录、导出完整档案 | ✓ | ✗ | ✗ |
| 更改账号、成员、权限、历史分支 | 仅产品授权的接口 | ✗ | ✗ |

**安全边界：** 房间成员关系和角色操控权单独存储，不随剧情回档恢复。移除角色会清除其分配；回档恢复该角色后，由房主重新分配。

## 5. 关键用户流程

### 5.1 开团与多人加入

```text
注册/登录 → 冒险大厅 → 创建房间
  → 选择世界预设或输入自定义前提
  → 确认主持模式 → 获得邀请码
  → 同伴登录并加入 → 房主分配角色 → 开始行动
```

- 邀请链接形如 `/?join=ABC123`。未登录时先登录，再加入。
- 默认提供“雾港·第十三盏灯”“余烬边境”两个原创预设以及空白世界。
- 房主默认绑定第一个预设角色，并可操作所有角色。
- 非成员不能读取房间信息，即使知道房间 ID。

### 5.2 一轮行动

```text
玩家声明行动
  → 服务端验证身份、角色、房间版本、请求ID、当前待处理状态
  → 记录行动和快照，增加行动轮次
  → 组装本房当前时间线的上下文
  → Gemini 提供世界知识与一致性建议
  → 决策模型输出 narration / facts / check
  → 服务端验证字段、范围与检定类型
  → 记录主持叙事；如有 check，进入待检定状态
  → 操控者或房主点击掷骰
  → 服务端生成随机数、执行规则、更新角色与快照
  → 双模型根据已确定结果补充叙事，不能重掷或追加同轮检定
  → 广播新状态
```

- 这里的“轮次”是已提交角色行动数，不是 D&D 的战斗轮或先攻顺序。
- 重试主持、投骰、聊天、补述不会额外增加行动轮次。
- 首版整房串行执行。主持处理中，新的写操作返回冲突，不排队偷偷执行。
- 待检定未处理时，不接受新的角色行动；场外聊天和自由掷骰可在房间不忙时使用。
- 场外聊天保存为事件，但不进入模型上下文或历史检索。

### 5.3 主持失败与人工接管

- 两个真实接口中任一个失败，显示失败阶段/安全错误信息，不静默切换为演示回复。
- 已提交的行动、骰子和属性变化不会因为模型失败而消失。
- 房主可重试未完成的主持；不会重复提交行动或重复掷骰。
- 房主补述可以结束本次未完成回复；不会自动改变属性，也不会自动取消已有检定。
- 服务重启后检测到未完成主持，保留状态并提示房主重试。
- API 配置状态只代表环境变量齐备，不代表真实服务已通过联网验证。

## 6. 通用轻规则 v1

### 6.1 角色数据

| 字段 | 含义与约束 |
|---|---|
| 姓名 / 身份 / 简介 | 32 / 32 / 1,000 字符以内 |
| 生命 / 生命上限 | 当前值 0–上限；上限 1–100；生命为 0 不可再声明角色行动 |
| 压力 | 0–6；到达上限只记录与提示，不自动触发疯狂或额外规则 |
| 力量、敏捷、学识、洞察、魅力 | 各为 −3 至 +5 的检定修正值，不是 D&D 能力值 |
| 物品 | 最多 24 件，每件 1–60 字符；由房主维护 |
| 操控者 | 当前房间成员；与叙事状态分离存储 |

### 6.2 检定规则

`结果 = 服务端 d20 + 提出检定时的属性修正`

- 总结果 ≥ 难度则成功；难度范围 8–20。
- 天然 20 为大成功；天然 1 为大失败。此处是自定义轻规则，不声明与某本规则书完全相同。
- 待检定固定属性修正值；等待期间禁止改动该角色的属性。
- 失败代价只允许三种：`none` 无属性变化；`harm` 生命 −1；`stress` 压力 +1。
- 代价事先显示在检定卡片中；生命最低 0，压力最高 6。
- 大成功/大失败暂不叠加额外伤害或奖励，后续可扩展规则包。
- 模型不能直接提供骰子结果、任意生命增减、删物品或修改权限。

### 6.3 自由掷骰

支持 `1d20`、`2d6+1` 等表达式；1–20 颗骰、2–100 面，修正 ±100。

随机数使用服务器端 `secrets` 生成；客户端不能上传一个结果冒充掷骰。结果可追溯，但不是带种子承诺的可公开验证公平协议，也不宣称数据库管理员无法篡改。

## 7. 双模型设计与职责隔离

### 7.1 知识顾问：Gemini

输入：公共世界前提、叙事基调、当前角色与规则、近期有效事件、关键词召回证据、当前行动/骰子结果。

输出：简短的设定提醒、因果限制、可利用线索与一致性建议。它不能决定账号权限，也不能将自己的输出直接写入游戏数据库。

Gemini 适配器采用原生 REST `generateContent`，密钥通过 `x-goog-api-key` 请求头发送。该接口与返回的候选内容/文本结构可参见官方迁移文档：[4](https://ai.google.dev/gemini-api/docs/migrate-to-interactions)。模型 ID 由部署者填写，以其账户实际可用列表为准，不把某个型号永久写死。

### 7.2 决策模型：OpenAI 兼容适配器

输入：同一份权威上下文 + Gemini 顾问建议。

输出契约：

```json
{
  "narration": "面向玩家的中文叙事",
  "scene_title": "可选的场景标题",
  "facts": ["本轮已确认的事实，不包括未经证实的传闻"],
  "check": {
    "attribute": "insight",
    "dc": 12,
    "reason": "辨认钥匙柄上的印记",
    "risk": "none"
  }
}
```

`check` 可以是 `null`。服务端将检定绑定到本次行动角色，拒绝额外字段、未知属性、超范围难度、非法风险类型，以及骰后叙事再次提出检定的输出。

- 接口路径：`{DECISION_BASE_URL}/chat/completions`。
- 通过环境变量配置服务地址、模型 ID、密钥与 JSON 模式。
- 不支持 `response_format` 的兼容服务可关闭 JSON 模式；服务端仍严格验证响应。
- “jev”若不是该兼容格式，需新增适配器。模型身份未知不影响房间、权限、状态和历史核心开发。

### 7.3 事实与提示注入边界

- 用户行动、世界书、对白与检索证据被当成数据，而不是能够覆盖系统规则的指令。
- 结构约束只能保证格式和状态操作范围，不能保证叙事事实正确，也不能彻底消除提示注入。
- 世界书与服务器状态是优先依据；房主通过补述、角色维护或回档纠正错误。
- 首版世界书公共可见；不把“秘密”写进去后寄希望于模型替你保密。

### 7.4 成本与延迟

当前真实模式每次主持执行“知识顾问 + 决策”两次串行调用。有检定的完整行动通常需要 4 次外部调用：行动后 2 次、骰后叙事 2 次；重试也可能再次产生费用。

- 每个接口默认超时 45 秒，总流水线可能更长；并非固定低延迟保证。
- 首版有限制近期事件与召回条数，但没有 token 精确预算、费用账本或每租户硬额度。
- P1 优先做知识摘要缓存、token 预算、用量统计、费用上限与骰后知识复用，验证两模型是否确实优于单模型。
- 不为“顶级模型”而强行让所有环节使用昂贵模型；实际质量由试玩数据决定。

## 8. 事件、快照与回档

### 8.1 权威状态

```text
世界：名称 / 前提 / 基调 / 世界书条目
场景：标题 / 最新主持叙事
角色：属性 / 生命 / 压力 / 物品 / 简介
剧情：已确认事实 / 行动轮次
流程：待检定 / 未完成主持 / 后续叙事输入 / 错误状态
```

这些数据由服务端存储为房间当前状态。每个有效事件同时保存该事件发生后的完整状态快照。

### 8.2 事件字段

`id, room_id, seq, branch, active, type, actor_id, actor_name, character_id, text, payload, snapshot, created_at`

事件类型包括：开场、角色行动、主持、骰子、场外聊天、角色变更、世界书变更、系统、人工补述、回档、错误。

- `seq` 是全房间单调递增序号，不因回档重复。
- `branch` 记录事件产生时的分支。
- `active=1` 表示属于当前有效时间线；封存事件保持可审计，但不进入当前检索。
- 当前状态更新和事件写入处于同一个 SQLite 事务中。
- 事件记录与封存状态不等于防篡改日志；未来可加哈希链与审计权限。

### 8.3 回档语义

1. 仅房主能选择当前有效时间线中的节点。
2. 恢复该事件**完成之后**的快照，而不是该事件之前。
3. 该节点之后的有效事件全部封存；不物理删除。
4. 分支号递增，追加一条回档事件，广播给所有成员。
5. 重建上下文时只查询有效时间线，不带上封存的未来。

**随回档恢复：** 世界书、角色叙事数据、生命/压力/物品、当前场景、事实、行动轮次、待检定与未完成主持状态。

**不随回档恢复：** 账号、登录会话、房间成员、房主身份、当前操控分配、API 密钥、主持运行模式、幂等请求记录。

若回到一个“行动已提交但主持尚未完成”的节点，房间恢复为等待主持；房主可以重试或补述。已完成的旧请求 ID 不重复执行，重新选择/投骰使用新的请求 ID。

### 8.4 验收反例

“回档后消息不见了，但角色仍少 1 点生命”“世界书仍是未来版本”“旧线索还能被检索到”“旧权限重新生效”均视为失败，不能只凭界面看起来正常验收。

## 9. 上下文检索与持久记忆

### 9.1 已实现的方法

- 严格以 `room_id` 隔离房间。
- 世界书、当前已确认事实、有效历史事件组成候选资料。
- 中文按连续双字词、英文按词项匹配计分；标题/关键词参与匹配，世界书权重略高。
- 主持请求召回最多 6 条证据；组合最近 10 条非场外/非错误的有效事件。
- 最近事件单条输入截断至 1,500 字符；搜索界面最多返回 20 条结果。
- 事件列表显示最近 200 条；数据库保存完整事件，搜索遍历有效事件，导出含所有时间线与快照。

### 9.2 不冒充已经完成的能力

没有向量 embedding、外部向量数据库、自动知识图谱、跨房间语义记忆、自动全局摘要或 token 计费。关键词检索会漏掉同义表达，长房间的扫描和快照存储需要后续优化。

### 9.3 P1 改进顺序

先用真实试玩事件评估关键词召回，再决定是否引入 SQLite FTS、混合召回与 embedding。任何新索引必须支持房间隔离、分支过滤与回档失效，不能只做“向量搜索看起来很高级”。

## 10. 技术架构与数据设计

```text
React / Vite 浏览器界面
  ├─ 同源 REST：登录、房间、操作、检索、导出
  └─ WebSocket：鉴权后接收房间状态与在线成员
                ↓
FastAPI 单进程服务
  ├─ 账号、成员与角色权限校验
  ├─ 房间锁 + revision + request_key
  ├─ 轻规则、骰子与结构验证
  ├─ 有效时间线检索
  └─ Gemini / OpenAI 兼容模型适配器
                ↓
SQLite WAL：users / sessions / rooms / members /
             assignments / events / receipts
```

### 10.1 技术选择

- 前端：React 19、Vite、本地打包图标与静态资源；不依赖浏览器加载外部 CDN。
- 后端：Python、FastAPI、Uvicorn、HTTPX。
- 数据：SQLite WAL；适合首轮小规模单机、朋友间测试。
- 通信：一个同源服务同时提供页面、API 和 WebSocket，浏览器不访问服务器的 localhost。
- 部署：预构建静态文件 + Python 服务；另提供 Docker 多阶段构建与持久数据卷。

### 10.2 核心表

| 表 | 责任 |
|---|---|
| users | 登录身份、显示名、带随机盐的 scrypt 密码摘要、游客标记 |
| sessions | 服务端只保存随机登录令牌的 SHA-256 摘要与有效期 |
| rooms | 房主、邀请码、当前状态、revision、branch、主持模式 |
| members | 房间成员关系，不纳入叙事回档 |
| assignments | 角色操控关系；一个成员最多一个角色，不纳入叙事回档 |
| events | 事件内容、结构元数据、完整快照、时间线有效性 |
| receipts | 房内用户请求 ID 幂等记录，避免重复行动或重复掷骰 |

### 10.3 并发策略

写操作携带 `expected_revision` 与 `request_key`。同房间在主持处理期间不接受第二个写操作；落后版本返回 409，提示刷新。请求 ID 重复时不再次执行。

当前锁、在线状态与限速器在内存中，因此必须 `--workers 1`。扩容前需把互斥、消息广播、幂等一致性和限速迁移到分布式基础设施，而不是直接把 worker 数调大。

## 11. 页面与交互

1. **入口 / 冒险大厅**：登录、注册、明确的演示试玩、已有房间、创建/加入。
2. **冒险现场**：场景概览、事件流、主持链路、行动/场外输入、待检定、人工补述、实时同步状态。
3. **世界书**：前提、基调、公共条目、已确认事实与轻规则说明。
4. **角色档案**：属性、生命、压力、物品、操控者；房主维护与分配。
5. **事件档案**：检索、有效与封存记录、节点回档、完整 JSON 导出。
6. **主持设置**：两模型职责、已配置/未配置状态、模式切换、服务端配置说明。
7. **队伍侧栏**：实时状态与成员在线情况；手机上以抽屉打开。

设计原则：暗色酒馆氛围但文字清晰；铜金表示主持与时间线，绿色表示角色状态；不放无作用的装饰按钮。`Ctrl/⌘ + Enter` 发送，`Esc` 关闭弹窗。复制受浏览器限制时提供可手动选择的链接文本。

## 13. 非功能要求与当前限制

### 13.1 已有保障

- 密码使用随机盐与 scrypt 摘要；服务端不保存明文登录令牌。
- 前端在 `sessionStorage` 保存本次会话的 Bearer 令牌；退出后失效。没有把令牌拼入 WebSocket URL。
- API 密钥只在服务端环境变量中；状态接口、快照、导出不含密钥。
- 输入长度/数值范围验证、角色与房间权限校验、请求幂等、SQLite 事务。
- 登录、注册、创建房间、行动、聊天与自由骰子有进程内限速。
- 页面使用 React 文本渲染和内容安全策略，不把模型文本直接当 HTML。

### 13.2 私人测试可用，不等于已生产就绪

公开上线前需要补齐：HTTPS 与访问策略、账号验证/找回、邀请撤销、成员移除、费用额度、长期会话与日志清理、备份恢复演练、监控和安全审计。

当前令牌对同页脚本可读，XSS 风险仍存在；高风险部署应改用适当的 HttpOnly Cookie 会话与 CSRF 保护，或更完整的鉴权系统。没有公开注册下的模型消费硬上限，不建议把付费密钥接入完全开放的公网服务。

### 13.3 性能目标（待真实负载验证）

- 近场小规模测试中，以“其他玩家无需手动刷新即可收到状态”为同步验收标准。
- 真实模型延迟和质量受服务商、网络、上下文与配额影响，不以固定秒数承诺。
- 每事件完整快照会增加存储量；长团需摘要、增量快照与索引优化。
- 不声称支持海量并发、分布式部署或故障自动切换。

## 14. 验收标准

| 编号 | 测试 | 通过标准 |
|---|---|---|
| A01 | 两账号加入同房 | 互相看到成员与房内公共状态 |
| A02 | 未授权读取/操作 | 非成员不能读；玩家不能改他人角色、设定或回档 |
| A03 | 角色分配 | 分配后玩家能行动；改分配后旧玩家不能继续操控 |
| A04 | 行动与检定 | 有效行动只记一次；待检定阻断下一次行动 |
| A05 | 服务端骰子 | 结果、修正、难度、代价可追溯；不能由客户端指定结果 |
| A06 | 幂等与并发 | 重复请求不重复投骰；同时提交同版本最多一个成功 |
| A07 | 双模型接口 | 两阶段调用、结构输出校验、真实来源标记；失败不伪造成功 |
| A08 | 状态回档 | 恢复场景、世界书、属性、物品、轮次与待处理流程 |
| A09 | 记忆隔离 | 封存事件和他房事件不被当前上下文召回 |
| A10 | 权限不回退 | 回档不复活旧成员、旧登录或旧操控权限 |
| A11 | 中断恢复 | 模型失败或重启后数据仍在，房主可重试/补述 |
| A12 | 导出 | 有完整事件与快照，无密码/登录令牌/API 密钥 |
| A13 | 浏览器体验 | 桌面与手机不横向溢出；核心按钮和弹窗实际可操作 |
| A14 | 真实模型质量 | 用真实密钥跑完至少一场团；检查设定一致性、检定合理性与成本 |

A14 是交付后的必要验收：目前无真实密钥，不把模拟服务测试视为真实 Gemini 或未知“jev”的效果验证。当前测试结果见 `TEST_REPORT.md`。

## 15. 后续路线与决策门槛

### P1：稳定性与真正的长期跑团

1. 首先完成真实双模型联调、提示与结构兼容性测试，统计每轮费用与延迟。
2. 用 3–5 场真人试玩验证“规则受控 + 回档可靠”是否比普通共享聊天有价值。
3. 增加成员移除、邀请码轮换、秘密线索与按权限隔离的上下文。
4. 知识缓存、摘要、token 预算、费用硬上限、错误自动重试策略。
5. 搜索分页、FTS/混合检索、增量快照、快照恢复与导入工具。
6. 选一种具体规则包，先实现并测试检定/伤害/状态，再扩展完整战斗。

### P2：体验与扩展

地图与战棋、语音、可选角色卡/世界书导入、可切换的分支树、规则/模型适配器插件、多节点部署。

**停止扩张的条件：** 若玩家最常需要的是“简单房间 + 骰子 + 人类主持”，则优先做好辅助主持；若双模型没有明显降低设定错误或提高体验，不坚持复杂流水线。产品以真实游玩反馈为准，不以功能清单长度为准。
